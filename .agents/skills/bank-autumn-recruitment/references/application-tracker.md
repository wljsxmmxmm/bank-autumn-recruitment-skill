# 秋招投递表格与提醒规范

这是首发 MVP 的核心功能。用户要求“生成秋招投递表”“做类似截图的校招表”“定期跟踪投递”时，优先读取本文件。银行秋招场景必须先生成 Markdown 预览，用户确认后再创建到用户常用在线文档。

## 核心原则

- 先生成 Markdown 预览，再做在线文档；表格是秋招操作台。
- 银行秋招追踪表必须使用 `scripts/generate_tracking_table.py` 生成，不接受 Agent 手写排序后的表格。
- 用户要求“尽可能全面”“覆盖大部分银行”“先给银行池”时，使用脚本内置 `comprehensive` 模板生成机会池骨架，再按用户城市、岗位类别和简历竞争力删减。
- 表头必须符合银行秋招追踪字段；同一家银行不同分行必须拆成多行。
- 为了能跟踪和提醒，字段要覆盖岗位来源、银行/岗位信息、关键时间、材料、笔试面试、提醒复盘、offer/签约风险。
- 当前岗位开放状态、截止日期、官方标题和投递链接必须联网核验或由用户提供来源；未核验填 `待验证`。
- 不追求一次性填满所有岗位；先建可筛选、可复盘、可持续更新的表。
- 银行 Demo 默认覆盖银行通用校招，不只限产品/运营/数据。

## 银行秋招默认全面字段

| 字段 | 用途 | 填写规则 |
|---|---|---|
| 信息来源 | 岗位从哪里来 | 银行官网/分行官网/学校就业网/校招平台/官方公众号/内推/宣讲会/待验证 |
| 投递链接 | 官方公告或投递入口 | 优先官方链接；没有则写 `待验证` |
| 银行名称 | 银行或机构名称 | 使用常见简称，保持一致 |
| 银行类型 | 政策性银行/国有六大行/股份制银行/城商行/农商行 | 不确定写 `待验证` |
| 梯队 | 第一/第二/第三/第四梯队 | 见 `bank-tier-strategy.md` |
| 岗位名称 | 具体岗位 | 使用公告原岗位名；未核验写 `待验证` |
| 岗位类别 | 管培/金融科技/数据分析/运营/风控/客户经理/柜面等 | 按用户主投类别归类 |
| 分行/总行 | 总行、分行、子公司或机构 | 不同分行单独一行 |
| 工作地点 | 城市或区域 | 多地可写 `多地`，不确定写 `待验证` |
| 招聘批次 | 提前批/正式批/补录/春招/暑期实习/实习转正 | 不确定写 `待验证` |
| 网申截止日 | 网申截止 | 必须核验；不确定写 `待验证` |
| 网申账号 | 登录账号或入口备注 | 可写邮箱/手机号尾号/待创建；不要写完整敏感密码 |
| 简历版本 | 使用哪版简历 | 银行业务版/金融科技版/风控版/城市分行版等 |
| 材料清单 | 投递所需材料 | 简历/成绩单/证书/就业推荐表/生活照/证件照等 |
| 网申提交日 | 实际提交日期 | 未投写 `未投` |
| 笔试时间 | 笔试或测评时间 | 未公布写 `待公布`，不猜 |
| 测评状态 | 性格/能力测评进度 | 待完成/已完成/无需/待验证 |
| 笔试状态 | 笔试进度 | 待通知/待准备/已参加/通过/未通过/缺考/待验证 |
| 面试轮次 | 当前面试阶段 | 群面/一面/二面/终面/HR面/体检/待通知 |
| 面试时间 | 已知面试时间 | 未通知写 `待通知` |
| 面试形式 | 无领导/半结构化/结构化/业务面/线上/线下 | 不确定写 `待验证` |
| 投递状态 | 当前进度 | 待核验/未投/已投/测评/笔试/面试/体检/offer/拒绝/放弃 |
| 下次跟进日 | 下一次处理日期 | 截止前、投后 7 天、笔面试前后都要更新 |
| 提醒级别 | 行动紧急度 | 今日处理/3天内/本周/观察/无需提醒 |
| 上岸概率 | 相对区间 | 用区间，例如 `40%-55%`；不要写精确承诺 |
| 关键证据 | 为什么值得投 | 简历匹配点、实习、证书、城市稳定性等 |
| 主要风险 | 最大不确定性 | 学历/专业/实习/笔试/地域/岗位真实内容/竞争强度 |
| 复盘记录 | 每次更新后的结论 | 记录拒绝原因、卡点、面试反馈、材料调整 |
| Offer状态 | offer 和结果 | 无/意向/offer/待签/已签/拒绝/放弃 |
| 签约风险 | 三方、违约、户口、轮岗、试用期等 | 只列待核验问题，不给法律结论 |
| 备注 | 证据、风险或下一步 | 标明待核验事项 |
| 优先级 | 投递顺序 | P0/P1/P2/P3 |

## 脚本使用

如果已有岗位候选列表，把列表整理为 JSON，再运行：

```bash
python3 scripts/generate_tracking_table.py --input rows.json --output tracking-preview.md
```

如果用户希望尽可能全面覆盖银行，先运行内置模板：

```bash
python3 scripts/generate_tracking_table.py --template comprehensive --output tracking-preview.md
```

该模板覆盖政策性银行、国有六大行、主要股份制银行、代表性城商行和农商行。模板是机会池骨架，不代表当年岗位已开放；`投递链接`、`网申截止日`、`笔试时间`、`工作地点` 等必须继续核验。

输入可以是 JSON list，或包含 `rows` 的对象。示例：

```json
[
  {
    "信息来源": "银行招聘官网",
    "投递链接": "待验证",
    "银行名称": "中国建设银行",
    "银行类型": "国有六大行",
    "梯队": "第二梯队",
    "岗位名称": "综合营销岗",
    "岗位类别": "运营管理",
    "分行/总行": "上海分行",
    "工作地点": "上海",
    "招聘批次": "秋招正式批",
    "网申截止日": "待验证",
    "网申账号": "待创建",
    "简历版本": "银行业务版",
    "材料清单": "简历、成绩单、证件照",
    "网申提交日": "未投",
    "笔试时间": "待公布",
    "测评状态": "待通知",
    "笔试状态": "待通知",
    "面试轮次": "待通知",
    "面试时间": "待通知",
    "面试形式": "待验证",
    "投递状态": "未投",
    "下次跟进日": "待安排",
    "提醒级别": "本周",
    "上岸概率": "45%-60%",
    "关键证据": "城市匹配强，有银行实习",
    "主要风险": "截止日和岗位说明待核验",
    "复盘记录": "待投递后更新",
    "Offer状态": "无",
    "签约风险": "待核验",
    "备注": "城市匹配强",
    "优先级": "P0"
  }
]
```

脚本会按 `梯队优先，同梯队内按上岸概率降序` 排序，并输出 Markdown 表。字段缺失时自动填 `待补充`。Agent 可以判断和补充候选岗位，但不能手写最终预览表。

全面模板生成后，必须提醒用户做二次筛选：

- 按目标城市保留本地城商行/农商行和目标分行。
- 按岗位类别保留管培、金融科技、数据分析、风控、运营、客户经理或柜面等主线。
- 对 P0/P1 银行优先核验官方招聘入口、开放批次和截止日期。
- 对不符合城市、学历、专业或工作偏好的银行标为 `观察` 或删除。

## 银行 Demo 字段建议

银行方向建表时，字段保持通用结构，但下列选项要优先出现：

- 投递类别: 总分行管培、金融科技、数据分析、产品经理、运营管理、风险合规、客户经理/营销、柜面/综合服务。
- 岗位族: 默认和投递类别一致；岗位横跨多类时可多选。
- 校招类型: 秋招提前批、正式批、补录、暑期实习、实习转正、春招。
- 投递通道: 银行招聘官网、总行/分行官网、学校就业网、校招平台、官方公众号、宣讲会、内推。
- 状态: 待核验、未投、已投、测评/笔试、面试、体检、offer、拒绝、放弃。
- 邮件提醒状态: 待发送、已发送、无需发送、发送失败。
- 邮件提醒原因: 新增可投、截止临近、今日处理、发送失败。
- 下一动作: 核验公告、确认分行/城市、准备银行版简历、完成网申、准备测评/笔试、准备半结构化/无领导、面后复盘、核验签约规则。

银行岗位的 `官方标题`、`来源链接`、`截止日期`、`城市/分行`、`岗位归属条线` 必须尽量回到官方招聘页或可信平台核验。无法确认时写 `待验证`。

## 提醒规则

默认用这些规则生成 `提醒级别` 和 `下一动作`：

- 截止日期已过且状态是未投/待核验: `今日处理`，下一动作是确认是否还能投。
- 截止日期 3 天内且未投: `今日处理`，下一动作是完成投递或放弃。
- 截止日期 7 天内且未投: `3天内`，下一动作是准备对应简历版本。
- 已投超过 7 天无反馈: `本周`，下一动作是查流程、补投同类岗位或复盘简历。
- 进入笔试/面试: `今日处理` 或 `3天内`，下一动作是专项准备和面后复盘。
- 已 offer/拒绝/放弃: `无需提醒`，下一动作改为沉淀经验或进入 offer 决策。

邮件提醒状态按这些规则维护：

- 新增可投岗位: `邮件提醒状态=待发送`，`邮件提醒原因=新增可投`。
- 截止日期 3 天内且状态为待核验/未投: `邮件提醒状态=待发送`，`邮件提醒原因=截止临近`。
- 邮件发送成功: `邮件提醒状态=已发送`，写入 `上次邮件时间`。
- 邮件工具不可用或发送失败: `邮件提醒状态=发送失败`，在复盘记录里说明原因。
- offer/拒绝/放弃: `邮件提醒状态=无需发送`。

## 默认筛选视图

生成表格后建议用户按这些视图管理：

- `今日处理`: 提醒级别为今日处理。
- `本周投递`: 状态为待核验/未投，且提醒级别不是无需提醒。
- `高匹配主攻`: 匹配等级为高匹配主攻，按截止日期升序。
- `流程中`: 状态为已投/笔试/面试。
- `结果复盘`: 状态为 offer/拒绝/放弃。

## 在线文档创建规范

只有用户确认 Markdown 预览后，才创建或更新在线文档。优先使用用户明确指定或常用的在线文档；当前环境只提供 Notion 时，使用 Notion。

当 Notion 插件可用且用户确认时，创建一个数据库，标题建议为 `2027 届银行秋招投递工作台`。银行秋招字段至少包含脚本输出的默认全面字段：

`信息来源`、`投递链接`、`银行名称`、`银行类型`、`梯队`、`岗位名称`、`岗位类别`、`分行/总行`、`工作地点`、`招聘批次`、`网申截止日`、`网申账号`、`简历版本`、`材料清单`、`网申提交日`、`笔试时间`、`测评状态`、`笔试状态`、`面试轮次`、`面试时间`、`面试形式`、`投递状态`、`下次跟进日`、`提醒级别`、`上岸概率`、`关键证据`、`主要风险`、`复盘记录`、`Offer状态`、`签约风险`、`备注`、`优先级`。

默认创建这些视图：

- `P0 主攻`: 筛选优先级为 P0。
- `本周处理`: 筛选投递状态为待核验/未投/测评/笔试/面试。
- `流程中`: 按投递状态看已投、测评/笔试、面试、体检等进展。
- `截止日历`: 用网申截止日做 calendar。
- `结果复盘`: 看 offer、拒绝和放弃记录。

如果在线文档工具不可用，保留 Markdown 预览并提示用户连接工具；不要声称已创建在线文档。

## 周复盘输出

每次定期跟踪时，至少输出：

```markdown
| 指标 | 本周数量 | 变化 | 判断 |
|---|---:|---|---|
| 新增岗位 | ... | ... | ... |
| 已投递 | ... | ... | ... |
| 笔试/面试中 | ... | ... | ... |
| offer/拒绝/放弃 | ... | ... | ... |
| 今日处理项 | ... | ... | ... |
```

然后给出：

- 本周最该处理的 3-5 个岗位。
- 需要补材料的岗位族。
- 下周投递和复盘节奏。
- 所有仍需核验的截止日期、链接和官方标题。
